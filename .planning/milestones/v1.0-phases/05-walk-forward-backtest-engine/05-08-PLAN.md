<objective>
Complete `backtest.py` by adding the simulate pass and run persistence: turn plan 05-07's
cached prediction rows into a staked, settled bet ledger, and write that ledger plus a
reproducible run manifest into a fresh `backtests/<run_id>/` directory.

This is the plan where the phase stops being plumbing and starts producing the artifact the
milestone is judged on. Everything before it computed a decision; this plan attaches money to
that decision, settles it, and writes down the number. Three things go silently wrong here if
they are not pinned: a stake computed from a bankroll that already knows the outcome, a CLV
whose sign was flipped on the way into the ledger, and a manifest that records a number
without recording the config that produced it — leaving a result that cannot be compared to
the current losing live configuration, which is the entire point of BT-05.

Purpose: BT-04 needs ROI, win rate and max drawdown reported on the flagged-bet subset with a
bet count and a confidence interval attached; BT-05 needs a reproducible, versioned run
manifest; BT-06 needs CLV per bet and in aggregate. The Kelly-fraction sweep (BT-07) is
deliberately NOT here — plan 05-09 owns it and re-simulates against the same cached
predictions this plan learns to stake.
Output: `backtest.py` (simulate pass + persistence), `tests/test_backtest.py`, and this plan's
rows filled into `05-VALIDATION.md`.
</objective>

<verified_facts>
<!-- Measured or read directly during planning. Use these; do not re-derive. -->

- `strategy.beregn_innsats` returns `0.0` exactly when `(odds-1)*p - (1-p) <= 0`, i.e. when
  `p <= 1/odds`. This is the RAW implied probability, while `vurder_kamp`'s value test uses the
  VIG-FREE one. A candidate can therefore pass the value threshold and still stake zero. That
  gap is real, is not a bug, and is why this plan counts `kandidater_uten_kelly_edge`: the flat
  arm of plan 05-09's sweep will place bets the half-Kelly arm skips, and the bet-count
  difference must be explainable from the manifest alone.
- `verdi_deteksjon.py:188` and `:202` write `Value` and `Forv. EV` as formatted percent strings
  (`f"{value:+.1%}"`), which `06_bot.py:287-288` copies verbatim into `bets.json`. The backtest
  ledger deliberately diverges here and stores raw floats, because `ledger.csv` is read by
  `metrics.py` while `bets.json` is read by the dashboard.
- `.gitignore` already excludes `bankroll.json`, `bets.json`, `nba_features.csv`,
  `odds_arkiv.db` and `dashboard.html`; plan 05-01 adds `backtests/` and
  `nba_spillerlogg_raw.csv`. No run artifact this plan writes is ever committed.
- `06_bot.py` settles pending bets at the START of the next daily run (`sjekk_resultater`,
  line 126) and places new bets afterwards (`plasser_bets`, line 240). A bet placed today is
  therefore never settled before the rest of today's bets are placed. The batched per-date
  settlement this plan specifies is not a backtest invention — it is what the live bot does.
- The smoke window plan 05-07 pinned (`fra="2022-10-24"`, `til="2022-12-31"`,
  `min_treningskamper=100`) yields `datoer_totalt` 66, skipped 15, processed 51,
  `kamper_totalt` 388, `retreninger` 2, `kamper_hoppet_over_manglende_odds` 0. Task 3 reuses
  exactly this window so its counters are comparable to plan 05-07's recorded smoke run.
- A full train/calibrate predict pass produces `datoer_behandlet` 303 over 13 retrain points
  and 2,302 games; exactly one game inside that slice (`2023-03-11` PHX vs SAC) has no closing
  snapshot, so at most one bet there can carry a `None` CLV. Plan 05-12, not this plan, runs
  the full pass.
- `numpy.float64` is not JSON-serialisable. Plan 05-03 casts every value it returns to a plain
  Python scalar for exactly this reason; this plan must not reintroduce a numpy value by
  computing anything itself instead of calling `metrics`.
