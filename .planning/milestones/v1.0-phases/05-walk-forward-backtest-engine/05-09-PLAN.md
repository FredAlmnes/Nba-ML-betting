<objective>
Add BT-07's Kelly-fraction sensitivity sweep to `backtest.py`: re-simulate staking at flat,
quarter, half and full Kelly against the prediction rows one walk-forward pass already
produced, and write the four arms into `backtests/<run_id>/kelly_sweep.json` alongside the
run's own `manifest.json`.

The sweep answers the one question the main manifest cannot: how much of the reported ROI is
the model's edge and how much is the staking rule. Two things go silently wrong here if they
are not pinned. First, re-running the walk-forward loop per fraction would produce four
*different* prediction sets from four *different* fits — the arms would then differ for
reasons unrelated to staking, and the comparison would be meaningless while looking perfectly
reasonable; Pattern 6 exists to prevent exactly that. Second, a sweep is a tuning activity by
definition, and tuning code that can reach the locked 2024-25 holdout burns BT-03's
spend-once guarantee without raising anything — which is why this plan's primary control is
that `kjor_kelly_sweep` has no argument capable of opening that window at all.

Purpose: BT-07 needs four distinct staking arms with ROI, max drawdown and bet count per arm,
derived from one predict pass. Everything the sweep stakes with already exists — plan 05-08's
`simuler_bets`, its `flat_innsats_belop` branch (D-05-03) and `metrics.oppsummer_ledger` —
so this plan composes, and re-derives nothing.
Output: `backtest.py` (sweep + writer + the `kjor_og_lagre` wiring), `tests/test_backtest.py`,
and `05-VALIDATION.md`'s last unassigned row filled in.
</objective>

<verified_facts>
<!-- Measured or read directly during planning. Use these; do not re-derive. -->

- `config.KELLY_FRAKSJON` is `0.5`, `config.STARTKAPITAL` is `1000.0`, `config.MIN_INNSATS` is
  `20.0` and `config.MAX_INNSATS` is `150.0` (read from `config.py` during planning). Under
  D-05-03's recommended option `flat_innsats_belop(1000.0)` is therefore `20.0`, which
  coincides with `MIN_INNSATS` — the flat arm sits exactly on the Kelly arms' floor, which is
  what makes the comparison readable.
- `strategy.beregn_innsats` returns `0.0` exactly when `(odds-1)*p - (1-p) <= 0`, i.e. when
  `p <= 1/odds` — the RAW implied probability, while the value threshold uses the VIG-FREE
  one. A candidate can pass the value test and still stake zero at every Kelly fraction.
  Consequence for this plan: **the four arms will not have identical bet counts.** The flat
  arm bets every flagged candidate; the three Kelly arms all skip the same Kelly-zero
  candidates (the zero test does not depend on `kelly_fraksjon`, only on `p` and `odds`), so
  quarter/half/full share one bet count and flat has a larger one. That difference is real,
  is not a bug, and must be explainable from `kelly_sweep.json` alone via each arm's
  `kandidater_uten_kelly_edge` counter.
- `kelly_fraksjon=0` is NOT a flat stake — `beregn_innsats` returns `0.0` for every bet at
  that fraction, producing an empty arm that reads as "flat staking loses nothing"
  (05-RESEARCH.md Pitfall 6). This is why D-05-03 defines the flat arm as a `backtest.py`-local
  branch and why `0` must never appear as a swept fraction.
- A full XGBoost + isotonic fit on ~2,500 rows takes ~0.4 s, and a full train/calibrate
  predict pass performs 13 retrains over 303 processed dates and 2,302 games (05-RESEARCH.md
  timing + plan 05-07's verified counts). So the predict pass costs roughly 10-15 s and each
  simulate arm costs pure arithmetic over a few hundred cached rows. Re-running the loop per
  fraction would quadruple the only expensive part of the phase to buy nothing — and, worse,
  would give the four arms four different fits.
- `05-PLAN-OUTLINE.md` estimates ~190-360 bets over the train/calibrate slice. Treat that as
  an order-of-magnitude expectation for plan 05-12's checkpoint, not as an assertion this
  plan may pin.
- `numpy.float64` is not JSON-serialisable. Every number written to `kelly_sweep.json` must
  come from `metrics.py` (which plan 05-03 requires to return plain Python scalars) or from a
  counter dict of Python ints — never from arithmetic performed in `backtest.py`.
- `.gitignore` already excludes `backtests/` (plan 05-01), so `kelly_sweep.json` never reaches
  git, exactly like `manifest.json` and `ledger.csv`.
- No new package is introduced. `json`, `copy` and `os` are stdlib; `metrics`, `config` and
  `backtest`'s own functions are already imported. `05-RESEARCH.md` §Package Legitimacy Audit
  records that the whole phase adds no external package.
